## Stage 0：基线测量　　2026-09-17

### 做了什么
搭好仓库骨架与配置体系；实现三层奖励函数并用 10 条边界用例自测；
用 vLLM 评测 Qwen2.5-1.5B（**Base**，非 Instruct）在 GSM8K 测试集前 500 题上的基线。

### 关键配置
| 项 | 值 |
|---|---|
| 模型 | Qwen/Qwen2.5-1.5B（Base） |
| 数据 | GSM8K test 前 500 题 |
| 采样 | temperature 0.8 / top_p 0.95 / max_tokens 700 / n=1 |
| 提示 | R1-Zero 风格 `<think>...</think><answer>...</answer>` |

### 结果
| 指标 | 数值 |
|---|---|
| **准确率** | **0.522** |
| 格式合规率 | 0.852 |
| 平均长度 | 164.7 tok |
| p95 长度 | 321 tok |
| 无法解析答案比例 | 0.060 |
| 分步推理词频 | 0.520 |
| **自我反思词频** | **0.006** |
| 验证词频 | 0.032 |

### 观察到的现象
- **基线远高于预期。** 原本按"Base 模型不会自发推理"预估 10–30%，实际 52.2%。
  原因是 Qwen2.5 的 Base 模型在预训练阶段就吃了大量合成数学数据，
  **"Base 模型不会推理"这个前提对这个模型族不成立。**
- **仅靠 prompt 就有 85% 格式合规**，模型能直接听懂 `<think>/<answer>` 的指令。
- **反思词频只有 0.6%**：模型会分步算，但几乎从不回头检查。这是真正的空白。
- 人工抽读了正确与错误各若干条，确认 52.2% 是真实推理能力，
  错误是真算错（看错题意、列错式子），**不是解析脚本的 bug**。

### 遇到的问题与解决
| 问题 | 根因 | 解决 |
|---|---|---|
| `hf download` 报 401 | 新版 `huggingface_hub` 默认走 Xet CAS 后端，`cas-server.xethub.hf.co` 不在 hf-mirror 代理范围 | `HF_HUB_DISABLE_XET=1` 退回普通 HTTP |
| 非交互 ssh 找不到 conda | conda 只在 `/etc/profile.d/` 注册，非登录 shell 不加载 | 脚本里显式 `source /etc/profile.d/conda.sh` |
| 两卡型号不同，GPU 编号可能错位 | 5090 与 6000D 混插 | `CUDA_DEVICE_ORDER=PCI_BUS_ID` 固定顺序 |

## Stage 1：跑通 GRPO　　2026-09-17

### 做了什么
TRL `GRPOTrainer` + LoRA + vLLM（server 模式，双卡分工）跑 200 步，
并在测试集上评测训练后的 LoRA。

### 关键配置
| 项 | 值 |
|---|---|
| G（每题采样数） | 8 |
| 有效 batch | 4 prompt/步 |
| 学习率 | 1e-6，constant + 10 步 warmup |
| KL 系数 β | 0.02 |
| 裁剪 ε | 0.2 |
| loss_type | dapo（token 级归一化） |
| LoRA | r=32, alpha=64, 7 个投影层 |
| 显卡分工 | GPU0 (5090) 跑 vLLM 采样，GPU1 (6000D) 训练 |
| 耗时 | 200 步 / 23 分 25 秒（约 7.0 s/步） |

### 训练曲线（每 40 步段落均值）
| 步段 | reward | r_answer | 格式合规 | 熵 | KL | 平均长度 | 反思词频 |
|---|---|---|---|---|---|---|---|
| 1–40 | 0.543 | 0.401 | 0.720 | 0.707 | 0.000 | 169.2 | 0.010 |
| 41–80 | 0.550 | 0.400 | 0.760 | 0.714 | 0.000 | 174.6 | 0.017 |
| 81–120 | 0.590 | 0.434 | 0.795 | 0.685 | 0.000 | 169.0 | 0.013 |
| 121–160 | 0.632 | 0.473 | 0.805 | 0.625 | 0.001 | 160.7 | 0.009 |
| 161–200 | 0.654 | 0.495 | 0.805 | 0.639 | 0.001 | 171.1 | 0.020 |

### 测试集结果（配对，同 500 题，McNemar 检验）
| 指标 | 基线 | 训练后 | 差值 | 新变好/新变差 | p 值 | 判定 |
|---|---|---|---|---|---|---|
| **答案正确率** | 0.522 | 0.550 | **+0.028** | 93 / 79 | **0.322** | **不显著** |
| **格式合规率** | 0.852 | 0.966 | **+0.114** | 71 / 14 | **1.2e-9** | **显著** |
| 无法解析比例 | 0.060 | 0.024 | −0.036 | | | |
| 平均长度 | 164.7 | 163.9 | −0.8 | | | |
| p95 长度 | 321 | 296 | −25 | | | |
| 反思词频 | 0.006 | 0.010 | +0.004 | | | |

### 观察到的现象 —— 本阶段最重要的结论

**1. 训练 reward 涨了，但涨的几乎全是"格式"，不是"推理能力"。**
训练批上的正确率从 0.40 爬到 0.50 看起来很好，但换到测试集上，
准确率只 +2.8 个百分点，**McNemar p=0.322，与噪声无法区分**。
配对数据说得更清楚：93 题新答对，79 题新答错，**净赚只有 14 题 / 500**。
反观格式合规率 +11.4 个点（p≈1.2e-9），是真实且强烈的提升。

> 这正是"训练 reward 上涨 ≠ 模型变强"的教科书案例。
> **只有配对检验能看出来**，只看两个准确率数字会误判成"提升了 2.8 个点"。

**2. 训练过程非常健康，没有任何失败信号。**
- 长度稳定在 170 左右，p95 甚至略降 —— **没有灌水 hacking**
- 熵从 0.707 缓降到 0.639 —— **没有熵坍缩**
- KL 全程 ≤0.001 —— 模型几乎没离开基座
- 零方差组占比稳定在 0.12–0.20 —— 采样浪费不严重

**3. 但"健康"恰恰解释了为什么没涨。** KL 只有 0.001 说明模型基本没动。
LoRA + lr=1e-6 + 200 步，加起来太保守了。

**4. 反思行为没有涌现。** 0.006 → 0.010，可以认为没变化。
1.5B 规模 + 200 步，**未观察到 R1-Zero 论文里的自我反思涌现**。

### 遇到的问题与解决
| 问题 | 根因 | 解决 |
|---|---|---|
| `GRPOConfig` 报 `max_prompt_length` 非法 | TRL 1.13 移除了该字段 | 删除；prompt 截断改由别处处理 |
| `GRPOConfig` 报 `logging_dir` 非法 | 同上，GRPOConfig 并非完整继承 TrainingArguments | 删除；TB 默认写 `output_dir/runs/` |
| `TensorBoardCallback requires tensorboard` | vLLM 和 TRL 都不依赖 tensorboard | `pip install tensorboard` |
| TRL 警告 vLLM 版本不兼容（支持 ≤0.28，实装 0.29） | 版本超前 | **实测可用**。警告 ≠ 不能用，但必须自己验证 |

**教训**：与其一个参数一个参数试错，不如**一次性把要传的参数对着 `dataclasses.fields()` 全量核验**。
第三次失败后改用这个方法，一次就过。

### 一个值得注意的指标定义差异
TRL 自带 `frac_reward_zero_std` 全程为 0，而我自定义的 `diag/zero_var_group_ratio` 是 0.12–0.20。
两者不矛盾：TRL 看的是**总奖励**的组内标准差（连续值，几乎不会恰好为 0），
我看的是**答案正确性**（二值，经常整组全对或全错）。
**衡量"采样是否被浪费"，我这个定义才有意义。**
